# Kanban WebUI → полноценный тасклист + Gitea

**Цель:** превратить доску из «окна в движок агентов» в личный тасклист, которым
пользуешься каждый день, и привязать к нему git-хостинг там, где задача про код.

**Исходная точка (проверено 29.10.2026):**

- `~/projects/hermes-kanban-webui` — форк `PriuS2/HermesKanban`, 69 тестов, RU, мобильный вид,
  токен, systemd-юнит. Читает и пишет `~/.hermes/kanban.db` через `hermes_cli.kanban_db`.
- Схема `tasks`: `id, title, body, assignee, status, priority, created_by, created_at, started_at,
  completed_at, workspace_kind, workspace_path, branch_name, project_id, tenant, result,
  idempotency_key, consecutive_failures, max_runtime_seconds, last_heartbeat_at, current_run_id,
  skills, model_override, provider_override, max_retries, goal_mode, session_id, block_kind,
  completion_contract, worker_started_at`
- Отдельные таблицы: `task_links`, `task_comments`, `task_events`, `task_runs`, `task_attachments`,
  `kanban_notify_subs`
- `~/.hermes/projects.db`: `projects(id, slug, name, description, icon, color, board_slug,
  primary_path, archived)` + `project_folders(project_id, path, label, is_primary)`. **Пусто.**
- Доски = отдельные файлы БД: `~/.hermes/kanban/boards/<slug>/`. Сейчас `default` и
  `notediscovery-android`.
- Gitea: `http://192.168.144.43:3000`, 3 публичных репозитория, токена в secrets нет.

## Чего не хватает для «тасклиста»

Честный список, по убыванию пользы:

| чего нет | зачем нужно | есть ли место в схеме |
|---|---|---|
| **срок** | без срока это список, а не тасклист | нет |
| **метки/контексты** | фильтр «только homelab», «только семья» | `tenant` подходит как «область», но не как метки |
| **вид списком** | доска хороша для потока, список — для «что на неделе» | нет |
| **сортировка по сроку** | «просрочено / сегодня / неделя» | нет |
| **проект** | группировка и связь с репозиторием | `project_id` есть, `projects.db` есть |
| **вложения** | чек, скан, скриншот к задаче | `task_attachments` есть, UI не показывает |
| повторяющиеся | «оплатить интернет» каждый месяц | Hermes cron уже есть — дублировать не надо |

Отдельно: **поиск**. Сейчас фильтрация идёт в Python по уже выбранным задачам; `list_tasks`
текстового поиска не умеет. Для сотни карточек это терпимо, для тысячи — нет.

## Центральное решение: где живут новые поля

Три варианта, выбор определяет всё остальное.

**A. Своя таблица внутри `kanban.db`** (рекомендую)

```sql
create table if not exists webui_task_meta (
    task_id   text primary key,
    due_at    integer,          -- unix, полночь локального дня
    tags      text,             -- JSON-массив строк
    updated_at integer not null
);
```

- один файл → один бэкап, джойны тривиальны, нет проблемы согласованности;
- Hermes не знает про эту таблицу и не трогает её; префикс `webui_` защищает от совпадения имён;
- минус: CLI и агенты срок/метки не видят (для личных задач это нормально).

**B. Отдельный `webui.db` рядом.** Ноль риска для файла Hermes, но каждый запрос — `ATTACH`,
бэкап из двух файлов, и расхождение возможно (задача удалена, метаданные остались).

**C. Колонки прямо в `tasks`.** Видно всем, но это правка схемы ядра: миграции Hermes добавляют
только свои колонки, а пересоздание таблицы (если когда-нибудь случится) молча унесёт наши поля.
Не рекомендую.

**Выбор: A.** Запись — только через WebUI; чтение — джойн в `board_view`.

## Этапы

### P0. Бэкап и таблица (0.5 ч)

1. `~/.hermes/kanban.db` копируется раз в сутки (`sqlite3 .backup`, не `cp` — на живой базе).
   Куда: `~/.hermes/backups/kanban-YYYYMMDD.db`, хранить 14 штук.
2. Миграция `webui_task_meta` при старте сервиса (idempotent `create table if not exists`).
3. Тест: таблица создаётся на пустой базе, повторный старт не падает.

**Файлы:** `kanban_webui/meta.py` (новый), `kanban_webui/app.py`, `bin/backup.sh`, юнит-таймер.

### P1. Срок и метки (3 ч)

- Поля в диалоге создания и в drawer: `due_at` (date input), `tags` (строка через запятую).
- На карточке: просрочено — красная плашка «−2 дн», сегодня — «сегодня», иначе дата.
- Фильтры в тулбаре: «Просрочено», «Сегодня», «7 дней», «Без срока» + фильтр по метке.
- Сортировка колонки по сроку (пустые в конце).
- API: `PATCH /api/tasks/{id}` принимает `due_at`/`tags` (расширение существующего тела).
- Тесты: мета пишется и читается, джойн в `board_view`, фильтры отдают правильные наборы.

### P2. Вид списком (2 ч)

Переключатель «Доска / Список» в шапке. Список — таблица: срок, метки, статус, исполнитель,
проект, заголовок. Сортировка по любому столбцу, те же фильтры. Это и есть «тасклист»:
доска отвечает «что в работе», список — «что на неделе».

### P3. Проекты (2 ч)

- Завести `projects.db` в оборот: WebUI показывает проекты, карточка получает `project_id`.
- `projects.primary_path` → локальный каталог → `git remote get-url origin` → репозиторий Gitea.
- Доска проекта: `projects.board_slug` связывает проект с доской (у Hermes это уже заложено).
- Решение по областям (см. вопрос 1) определяет, нужен ли `tenant` как область.

### P4. Gitea, только чтение (3 ч)

- Токен в `~/.hermes/secrets/gitea.token` (нужен `read:repository`, `read:issue`).
- На карточке с `project_id`: ветка, последний коммит, открытый PR, статус CI — из
  `GET /api/v1/repos/{owner}/{repo}/...`, кэш 60 с в `webui_gitea_cache`.
- Никаких записей в Gitea на этом этапе.

### P5. Gitea, действия (4 ч, только если P4 приживётся)

- Кнопка «Создать ветку» → `project/<slug>/<task-id>` (Hermes уже использует такой шаблон для
  проектов, имя совпадёт).
- Вебхук Gitea → приёмник (архитектура уже отработана на TaskView: HMAC, ответ сразу, тик):
  PR открыт → карточка в `review`; PR смержен → `done`.
- Осторожно: это второй источник правды по статусу. Включать, только если реально мешает руками.

### P6. Вложения (1.5 ч)

`task_attachments` уже заполняется Hermes. Показать список в drawer, отдавать файл через
`GET /api/tasks/{id}/attachments/{name}` с проверкой, что путь внутри `~/.hermes/kanban/attachments`.

## Риски

1. **Схема `kanban.db` принадлежит Hermes.** Наша таблица аддитивна и с префиксом, но после
   `hermes update` надо прогонять тесты и проверять, что `webui_task_meta` на месте.
2. **Личные задачи в базе агентов.** Диспетчер берёт только `ready` + assignee. Личная карточка
   без исполнителя не будет подхвачена — но она видна в `hermes kanban list`. Если это мешает,
   личные задачи уезжают на отдельную доску (и теряют общий поиск).
3. **Gitea без токена** — только публичные репозитории, действий нет.
4. **Рост `kanban.db`.** Сейчас ~50 задач, история событий уже 879 записей. Метки и сроки
   добавят мало, но бэкап из P0 нужен до любых изменений.
5. **P5 — единственный этап, который связывает две системы на запись.** Его можно не делать
   никогда, и ничего не сломается.

## Открытые вопросы

1. **Области: `tenant` или отдельные доски?** `tenant` — одна база, фильтр уже в UI,
   кросс-областные запросы («всё на неделе») работают сразу. Отдельные доски — полная изоляция
   файлов, но общего поиска и общего списка нет. Рекомендую `tenant`.
2. **Насколько глубоко Gitea?** Рекомендую остановиться на P4 (показать ветку/PR/CI), а P5
   делать только если руками станет неудобно.
3. **Срок: дата или дата+время?** Рекомендую только дату (полночь локального дня): для личных
   задач время суток почти всегда шум, а напоминания — это cron, а не поле.
